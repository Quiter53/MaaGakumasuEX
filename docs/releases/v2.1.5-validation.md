# v2.1.5 根因与验证记录

## 体力与 P 点数

旧商店读取已经限定爱心右侧并使用单行 OCR，但日程和 NIA 工作仍调用包含爱心的旧节点，解析逻辑也各自维护。失败后的业务处理有明确错误：日程把未知体力当作 `34/34`，工作把未知体力当作 `0`，日程把未知点数当作 `0`。这会让同一次 OCR 失败在不同页面产生相反决策。

现在 `agent/custom/cultivation_hud.py` 统一识别和严格解析，商店、日程/工作分别指定区域。不能直接照搬商店坐标：历史课程画面的数字行比商店偏低。三张历史图使用 MaaFramework 5.13.0 原生 OCR 回放，并调用最终生产读取函数核对：

| 画面 | 目视数值 | 最终读取 | 观察 |
| --- | --- | --- | --- |
| 商店一 | 21/33、119 P | 全部一致 | 旧区域读出 `♡21/33`，数字区域读出 `21/33` |
| 商店二 | 21/33、19 P | 全部一致 | 旧区域读出 `❤21/33`，数字区域读出 `21/33` |
| 历史课程 HUD | 17/30、330 P | 全部一致 | 过宽候选点数区域读成 `3307+`；按数字行边界裁切后读到 `330` |

以上证明已测像素与区域的效果，不证明所有体力未知均由同一原因造成。未知值不再被伪造；相关动作返回失败，由已有 `on_error → ProduceActionYield` 交回场景识别，不能走工作页成功分支中的通用点击。合法的 0 仍正常参与决策。调试日志保留尺寸、ROI、OCR 文本与分数、格式/范围错误，便于继续定位其他页面问题。

尚缺日程和 NIA 工作页的完整实机验证；未降低 OCR 门槛，未添加猜测数字、跨页面旧值缓存或额外重试循环。

## 出牌重复工作

主循环已有 `ProduceRecognitionCards` 结果，规则选牌却会在同一张图上再次检测。喝药前的组合判断和抬牌检查也会重复检测。现在显式传递 `CardDetection`，仅限同一帧、同一 Context；漏检结果同样复用，下一次截图重新创建观察对象。

身份匹配每次都重新计算固定参考图库的均值与平方和。现在只缓存这些固定统计量，按可见区域和匹配模式区分，最多 8 项，图库对象变化即清空。动态画面、查询特征和接受判断仍重新计算。

固定基线 `8c7e1ea` 与最终实现，在公开网页评估集 20 帧、65 个原模型牌框上交替运行 5 轮，最终身份字段、候选、分数、分差、拒识原因逐字段相同：

| 指标 | 原实现 | 新实现 |
| --- | --- | --- |
| 身份匹配总耗时中位数 | 1428.98 ms | 1187.53 ms |
| 额外参考统计缓存 | 无 | 约 1.31 MiB |

约 17% 仅为这个步骤的本机微基准，不含模型推理、截图、OCR 与动画，不能外推整局耗时。未改变重叠牌、角标牌的门槛或未知牌策略。

## 客户端与配置

- 选牌窗口不再因点选而重建所有控件；搜索复用卡牌按钮，合并同一 UI 周期的刷新。
- 黑白名单筛选只移除、插入或移动变化项，保留原对象。
- 名单文件按路径、纳秒修改时间及大小检测变化，损坏期间保留最近有效名单；不同路径不互相继承，恢复保存后生效。
- 更新检查不再重新请求已选 Release；保留跨页比较版本和稳定/测试渠道过滤，短末页结束，排除校验文件及未完成资产。
- 截图保存异步等待文件窗口，等待前保存当前图像快照，避免预览刷新后对象失效。
