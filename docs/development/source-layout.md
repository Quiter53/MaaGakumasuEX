# EX 培育源码组织

维护 EX 自己的实现，只参考上游按职责划分的方式。目录整理不同时引入上游策略、识别阈值或点击逻辑。

```text
agent/custom/
├─ action/produce.py       培育动作导出入口，保持框架注册与旧类名可用
├─ reco/                  自定义识别入口，包括 HIF
├─ hif.py                 HIF 共用页面识别、布局与日程辅助函数
├─ produce/
│  ├─ events.py           初、NIA 事件基类和剧本差异
│  ├─ options.py          工作、三选项、试镜及 HIF 属性/外出选项
│  ├─ battle.py           初、NIA、HIF 共用出牌策略
│  ├─ rewards.py          奖励选牌、HIF 换牌目标和原牌选择
│  ├─ shop.py             商店、删牌、HIF 幕间购物及商店进出
│  ├─ lifecycle.py        开始初始化、预算重置、断线和失败恢复
│  ├─ shared.py           共用名单读取、诊断、断线检查和奖励预算
│  └─ memory/
│     ├─ actions.py       回忆识别/动作注册入口
│     ├─ modes.py         模式、会话、目标及回忆读取
│     ├─ flow.py          常规回忆选择与再生成流程
│     ├─ farming.py       定向收集、筛选和进度保存
│     ├─ diamond.py       钻石词条识别
│     └─ memory_badges.npz 原有回忆标记素材
└─ card_visual.py 等       各场景共用的卡牌、饮料、牌组及几何识别
```

## 放置规则

- 同一种职责集中维护。初、NIA、HIF 的相同算法只保留一份；剧本差异通过配置、类属性、子类或已存在的 HIF 对应类表达。
- `action/produce.py` 只负责导出，不重新积累业务逻辑。新增动作放入对应职责模块，框架注册名保持唯一。
- 页面识别辅助函数复用 `hif.py`、`card_visual.py`、`deck_scan.py` 等既有模块，不为一个小选项再建一套相似识别代码。
- 跨职责确实互相调用时，仅在调用方法内导入所需类，避免循环导入；不使用动态执行、全局命名空间注入或复制类解决依赖。
- 回忆内部实现和素材集中在 `produce/memory/`。移动文件时必须核对基于 `__file__` 的路径，个人配置和进度仍指向运行目录原有的 `config/`。
- 流程 JSON 继续按初、NIA、HIF 分开，共用节点留在 `ProduceUtils.json`；任务配置继续使用现有选项树。
