# 任务日志循环检测与结果通知

本次改动用于本机 2.0.3 pre，正式版 latest 保持 2.0.2。

## 检测与停止

- 仅在框架任务执行期间监测，不监测空闲、更新下载或附加脚本。
- 连续 5 分钟没有任务日志，停止本轮任务队列。
- 同一条或一组 1～16 条日志按循环顺序持续重复至少 3 分钟，并累计至少 30 条重复记录，停止本轮任务队列。
- 使用单调时钟。任务切换、实际日志内容变化、进入或退出手动确认弹窗都会重置相应计时；各实例互不影响。
- Python 原始 INFO 及以上日志通过独立的内部消息送入检测器，早于简洁显示过滤；原生流水线的成功动作事件和任务日志也参与检测。详细日志开关不会关闭检测，DEBUG/TRACE 噪声不会单独证明流程有进展。
- 归一化时间戳、重试计数及部分坐标、耗时、置信度字段；保留回合、卡名、数量和分数等业务变化。不改识别门槛或出牌规则。
- 触发后使用正常停止接口停止执行器、取消剩余队列，结果记为失败。保留游戏和助手，不执行成功后的关机、关闭游戏等操作。

日志是卡住的证据，不能证明所有类型的死循环。持续生成不同业务日志或不规则长循环可能不满足当前重复条件；没有日志的正常长等待也受 5 分钟限制。3 分钟循环门槛和 5 分钟静默门槛是当前默认策略，后续可依据现场记录调整。

## 结果通知

已有成功、失败通知入口仍使用用户配置的渠道。通知固定包含结果、任务名称、原因和耗时；自定义文本追加在报告后，不能掩盖真实结果。手动停止单独报告“已停止”。未配置通知渠道时不会发送。

修复“出错后继续”将底层失败隐去的问题：继续执行剩余任务的配置仍然有效，但最终结果记为失败，并保留首个失败任务；日志检测触发的停止优先记录对应原因。一般框架失败说明识别或操作未完成，不臆造具体 OCR 根因。

停止任务的取消令牌不会取消最终通知。通知单独限时 30 秒，成功后的退出操作等待通知发送完成。微信响应同时检查 HTTP 和业务结果，服务拒绝不再当作发送成功；服务接受也不等同于用户手机已读。

执行器停止确认最多等待 10 秒；若仍未确认，不会卡住通知流程，会在失败通知中明确说明队列已取消、执行器停止尚未确认，需要手动检查。

## 验证

- 原生编译通过，已有编译警告未新增。
- 639 项 Python 测试、339 个子测试通过，包含详细日志开关两种状态的原始消息一致性与多行消息处理。
- `tests/native_task_watchdog` 覆盖静默、单条及多条循环、真实回合变化、计时重置、手动等待、实例隔离、四种语言通知和微信业务拒绝。
- 以前的剧情循环真实动作日志回放在开始后 187.4 秒检出循环；回放沿用原时间戳，没有操作游戏。
- 新包另做 Agent IPC、资源入口和 ZIP 完整性检查。未新增实机长跑，也未向微信发送测试消息。
