# 2026-10-15 测试失败复核

本轮按要求更新出牌超时测试，并细查跨页换牌、饮料替换和商店恢复。修改范围为测试和本文档，未修改 agent、资源、用户配置或运行包。此前冗余清理的工作区改动保持原状。

## 结论

不能把此前 45 项失败全部归为“旧测试”。本轮纠正了 26 项旧测试预期或测试输入问题；换牌仍有 5 项真实策略差异，另外发现一个原测试没有覆盖的商店跨访问状态漏洞。

| 类别 | 根因 | 本轮处理 |
| --- | --- | --- |
| 出牌识别超时 | 旧测试要求整个动作失败；当前需求是交回培育入口继续识别 | 更新 2 项返回值预期，保留不出牌、不跳回合，增加不直接点击断言 |
| 跨页换牌 | 入口明确传 `strict=False`，遇到当前页合格牌立即结束，后页不参与比较 | 保留原 5 项失败；用隔离对照证明仅切换扫描模式即可通过，不修改正式策略 |
| 奖励饮料重复 | 旧测试要求删除重复目标饮料；现行策略允许重复且保护目标 | 更新预期，保留满栏非目标替换失败时禁止领取的保护 |
| 商店满栏替换和恢复 | 测试缺少回血、弹窗 OCR、数量回执输入；另有旧的返回失败预期 | 补齐输入，验证不再消费、不再丢弃以及取消购物后继续培育 |
| 同店重复删牌 | 把同一上下文、同一商品画面的第二次回调误当新访问 | 验证同店不重扫，显式新访问重置后才允许再次扫描 |
| 新商店被跳过 | 旧访问的 `exit_pending` 未在已验证的新日程进店时重置 | 已保存失败复现；运行逻辑尚未修复 |

## 跨页换牌：确实没有比较后面的牌

代码位置：`agent/custom/action/produce.py` 的 `ProduceHIFChangeSourceAuto.run`（约 5851 行）和 `_scan_source`（约 5922 行）。

`run()` 固定使用快速模式。扫描器在当前页找到允许换出的候选后直接返回，虽然候选符合名单许可，但不保证是全牌库中优先级最高的候选。相同输入下：

| 第一页 | 后页 | 当前正式入口 | 隔离完整扫描 |
| --- | --- | --- | --- |
| R 卡 | 黑名单 SSR | 第一页 R | 后页黑名单 SSR |
| 替换名单 SSR | 普通 R | 第一页替换 SSR | 后页 R |
| 替换名单 SSR | 替换名单 SR | 第一页 SSR | 后页 SR |
| R 卡 | N 卡 | 第一页 R | 后页 N |

同页候选之间的 N → 黑名单 → R → 替换名单排序仍存在，问题在于搜索范围提前结束。白名单等禁止条件仍执行，不能把“允许换”与“全局优先换”混为一谈。

保留以下原测试及断言，没有改成接受错误优先级：

- `test_later_r_card_precedes_first_page_replacement`
- `test_later_replacement_sr_precedes_first_page_replacement_ssr`
- `test_scroll_reacquires_card_box_before_submit`
- `test_end_of_scroll_does_not_count_a_nonexistent_page`
- `test_blacklist_found_lower_is_reacquired_on_current_page`

对照脚本只在独立测试进程中覆写扫描参数，原用例、原页面、原断言不变，5 项全部通过。证据位于 `D:/Codex/diagnostics/failure-audit-20261015/check_strict_scan.py` 和 `strict-comparison.log`。没有改动正式入口，也没有向游戏发送操作。

`docs/releases/v1.5.2.md` 仍写着跨页保留最优候选，和现在的快速入口有差异。若要求跨页优先级，需要恢复完整搜索或实现能证明没有更高优先级牌时才停止的扫描；只放宽识别阈值或更换匹配器无法解决。不要把这 5 项直接标成失效断言。

## 饮料：策略变化与测试输入问题

版本说明 `docs/releases/v1.5.2.md` 已明确允许同种饮料、满栏只用非目标腾位、全目标保留。实际奖励和商店路径符合这组规则：

- 未满且奖励是目标：直接领取，保留已有同名瓶。
- 满栏四瓶都是目标：跳过奖励，重复瓶也保留；缺少另一种目标不构成丢弃现有目标的许可。
- 满栏存在非目标：只在有可负担目标商品或目标奖励时腾位，丢弃前再次核实名称。
- 库存身份不明或丢弃结果未确认：不继续购买，不重复提交丢弃。

旧奖励测试还在模拟“先丢重复，再领一瓶”，与上述策略冲突。相关预期已更新。原来的“丢弃失败不能领取”用例改用确实需要丢弃的满栏非目标输入，保护断言保留。

其他测试修正：

- 给假 OCR 返回完整未命中结果，避免 `Mock.filtered_results` 被当列表遍历。这类异常出现在测试替身中，不证明真实 MaaFramework 返回了错误对象。
- 商店测试明确设为满体力，保留实际入店/离店回血检查，只让它自然无需消费。新增测试明确要求正常离店仍调用 `spend_remaining=True`。
- 奖励丢弃后的数量来源已改为奖励页面专用识别，旧测试还模拟商店占用格；现在模拟正确数量入口，并保留连续两帧数量减少才成功的约束。
- 饮料标题与删牌核名测试原来传 `image=None`。现在使用有效截图输入，保留名称不符、稀有度不符时拒绝提交的断言。
- `expected_name=None` 是省略参数的默认值，删除对这种等价调用形式的强制要求，仍检查 `expected_non_target=True`。

本轮没有发现所测饮料替换场景需要修改正式策略。这里是逻辑测试结论，不代表识别模型或所有真实画面准确率验证。

## 商店恢复：正常保护与真实漏洞

`_finish_optional_shop()` 返回 True 表示让培育继续，并不表示购买成功。价格多次读不到、购买回执不明、刷新未确认等情况会取消本次可选购物。新增跨回调测试确认：

1. 退出点击被吞、商店还在时保留退出意图，新 action 实例不重新扫描、购买、刷新或丢弃。
2. 有取消弹窗时先取消，再走离店，不点击购买确认。
3. 退出任务本身报告成功还不够；必须连续两帧不再显示商店才清除退出和回血待核状态。
4. 停止或断线时不点击恢复控件。
5. 饮料已提交丢弃但弹窗尚未退出时，后续回调不再丢弃、不领取旧位置奖励、不盲点跳过。

**新增漏洞复现：旧访问的退出意图会影响新访问。**

复现顺序：

1. 旧店调用退出，嵌套任务报告成功，但随后的四帧仍显示商店，保留 `exit_pending=True`。这一行为本身正确。
2. 旧店稍后完成退出，流程最终抵达下一次咨询日程。
3. 真实 `ProduceHIFEnterShopAuto` 在两次稳定识别后点击日程，并观察到两帧页面推进。它只重置删牌检查状态，没有重置 `automatic_visit.exit_pending`。
4. 新 `ProduceShoppingAuto` 一进入就命中旧退出标记，直接离店；商品扫描调用次数为 0。

测试期望 `(旧退出标记=False, 新店扫描次数=1)`，实际为 `(True, 0)`。证据：`D:/Codex/diagnostics/failure-audit-20261015/test_shop_visit_lifetime.py`、`visit-lifetime.log`。这是一项确定可复现的状态生命周期问题，不是 OCR 置信度或原测试过时。

修复应把退出意图、回血待核、删牌检查的生命周期统一到商店访问，并在可靠的新访问边界清除上一店的状态；同店 JumpBack 或暂时识别不到店面时仍必须保留保护。不能简单地每次回调清空状态，否则会重新引入重复花钱风险。本轮按调查范围保留运行实现，失败复现单独保存，未用跳过或预期失败标记掩盖。
