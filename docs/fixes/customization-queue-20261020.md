# 自定义完成后的重复扫描与遮罩余额读取

## 现场

2026-10-20 的业务日志：

- 17:19:11 开始脚光选项 2，自定义前余额 465。
- 17:19:14 确认完成，余额 395，扣款 70。
- 17:19:19 再次进入自定义扫描后，提示“选中卡名称未确认”。
- 17:19:21 已返回商店并选择初星黑醋；17:19:24 余额变为 295。
- 17:19:25 用户停止，饮料交易确认返回 stopped。

因此，脚光已经成功，警告来自成功后的重复扫描，不是该笔自定义扣款失败。
14:49 也有同样的“脚光完成 → 选中卡名称未确认”记录。

用户提供的截图经本地 MaaFramework 5.13.0 无输入回放：

- 自定义列表、未选中卡牌，`name=None`，剩余额度 1。
- 顶部 HUD 被列表遮罩模糊，不能作为此页面的余额读取依据。
- 第一列第三行的 `カスタマイズ済`，坐标 `[78,905,120,24]`，OCR 分数 0.999307。

## 根因

1. 原来使用“先快做第一张，再返回列表全量扫描”的混合流程。
   第一张完成后无条件重新进入，即使它已经是唯一目标。
2. 列表扫描仍可能点击标有“已自定义”的灰色卡，再要求读出选中标题。
   不可选卡没有标题，正常界面状态被误报为识别错误。
3. `purchase` 在菜单和预览页面调用顶部余额 OCR，把页面遮罩问题交给数字识别处理。
4. 成功确认后还默认留在菜单。游戏若直接返回商店，原逻辑会继续等待不存在的菜单。

这些问题属于流程状态与页面职责，不靠降低置信度、增加统一等待解决。

## 修复后的流程

1. 在清晰商店页确认余额和可用额度。
2. 首次进入时扫描一次，按设置优先级建立已确认的待办；同名实体副本继续按原扫描结果保留。
3. 逐项定位并核实目标，按用户设置补足次数。同一张牌仍留在菜单时，连续完成其需要的选项。
4. 菜单内只核对卡名、选项、价格和剩余次数；不读取遮罩下的 HUD 余额。
   精确的选项次数变化确认操作效果，按已确认价格更新会话内预计余额。
   此时仍保留待核销交易标记，不能把预计余额冒充真实 OCR。
5. 返回清晰商店后，实际余额连续两次与累计扣款一致，才清除待核销标记。
   若成功提示和真实扣款已经确认、游戏直接返回商店，已达到目标就结束该卡，不重新打开核查。
6. 还有待办才重新进入；没有待办直接转饮料。刷新沿用待办队列，不重扫已完成目标。
7. 额度用完或同卡剩余步骤需下一批继续时，先处理当前目标饮料；
   余额足够支付刷新及下一步费用，才按原商店规则刷新。
   余额不足、目标缺失或已达上限不凭空产生自定义刷新需求。

“已自定义”标签与卡牌坐标关联，只跳过对应卡。未知卡图且无法确认标题时跳过该候选，
不影响其他已确认目标，也不把未知候选作为付费刷新的依据。
已识别目标出现卡名冲突、扣款不一致等情况仍保留交易保护，不重复提交。

特别指导继续使用自己的额度、余额观察及退出流程；不把商店队列和刷新逻辑套到特别指导。
未提交操作前的短暂余额未知保持可重试，不当作余额为零，也不永久封锁本店自定义。
若初始页面意外已是遮罩列表，必须先退出再交给饮料流程，不返回旧截图继续购物。
