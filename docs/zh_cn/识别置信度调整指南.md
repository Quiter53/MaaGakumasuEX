# 识别置信度调整指南

适用：MaaGakumasu EX 的 Windows 便携版和源码版。本文按 **v2.1.2 预发布版代码**核对，包括商店体力、P 点数的固定数字框修复。v2.1.1 包中部分函数仍为旧实现，请先核对文件，不要跨版本套用。

本指南说明手动修改方法，不会自动调整用户的识别阈值。

## 1. 先找到实际运行的文件

源码目录与运行包目录不是同一个地方。只修改源码，已经解压的运行包不会自动变化。

| 内容 | 源码中的路径 | 便携包中的路径 |
| --- | --- | --- |
| Python 识别与业务逻辑 | `agent/custom/…` | `agent/custom/…` |
| 基础流水线 | `assets/resource/base/pipeline/…` | `resource/base/pipeline/…` |
| 简中资源覆盖 | `assets/resource/zh_CN/pipeline/…` | `resource/zh_CN/pipeline/…` |
| DMM 资源覆盖 | `assets/resource/DMM/…` | `resource/DMM/…` |
| 手牌身份标定参数 | `agent/custom/hand_identity_calibration.json` | 同左 |

例如，本项目源码在 `D:\Codex\MaaGakumasu-card-strategy-git`，本地 pre 在 `D:\Codex\MaaGakumasuEX-pre`。普通用户应以自己启动的 `MaaGakumasu.exe` 所在文件夹为运行包根目录。

修改前停止任务并退出客户端，备份要修改的文件。修改后重新启动客户端，重新开始任务，使 Python 模块、识别资源和缓存重新加载。不要在任务运行途中修改。

## 2. 这些“分数”不是同一种东西

| 参数或表达式 | 含义 | 通常怎样放宽 |
| --- | --- | --- |
| OCR `row.score >= 0.90` | OCR 对文字结果的评分 | 降低 `0.90` |
| 普通模板匹配 `threshold`，例如 `method=5` | 图像与模板的匹配分数下限 | 降低下限 |
| 差异模板匹配，例如本项目 `method=1` | 图像与模板的差异上限，越小越像 | **提高**上限；方向相反 |
| 模型检测 `threshold` | 接受卡牌等检测框的分数下限 | 降低下限 |
| 卡图检索 `MIN_SCORE` | 与最相似卡图的相似度下限 | 降低下限 |
| `MIN_MARGIN`、`best_score - second_score` | 第一候选领先第二候选的差距 | 降低差距要求 |
| `MAX_KNOWN_DISTANCE` | 允许的颜色/特征距离上限 | 提高距离上限 |
| 名字 `similarity_ratio` | 两段文字的相似程度 | 降低相似度要求 |

**0.90 不代表经过校准的“90% 正确率”**。OCR、模板、卡图和颜色分类的分数不能横向比较。

以下参数不属于识别置信度：

- `roi`：识别框，格式为 `[左上角 x, 左上角 y, 宽度, 高度]`。
- `expected`：允许的文字正则或检测类别。内容不匹配时，分数再高也可能被拒绝。
- `only_rec`：是否直接识别已知文字区域，跳过文字位置检测。
- `post_delay`、`time.sleep`、出牌后等待时间：时间参数。
- 手牌可见面积、图片差异均值、颜色范围、连续确认帧数：几何或稳定性条件。
- 回血目标、投票门槛、卡牌优先级、最大购买次数：业务策略。

不要全局替换所有 `0.9`、`threshold` 或 `confidence`。

## 3. 为什么改了 JSON 可能没效果

一次识别通常经过以下几个环节：

1. 加载基础 JSON 节点，以及当前语言、平台资源和任务选项的覆盖。
2. Python 调用识别时，可能通过 `pipeline_override` 再覆盖参数。
3. MaaFramework 返回结果。
4. Python 再检查 `score`、名字、候选差距、坐标、页面状态和数值合法性。

这些条件需要一起满足。例如，框架接受 `0.85` 的 OCR 结果，但 Python 要求 `>= 0.90`，最终仍不采用。

另一个实际例子：`ProduceRecognitionExtraAction` 在 JSON 中写了 `0.72`，战斗代码调用时覆盖为 `0.35`，随后又用 `0.52` 和 `0.46` 判断“再动／非再动／未知”。只改 JSON 的 `0.72`，不能调整这条战斗判断路径。

搜索节点名时，应同时检查流水线、`agent` 和 `assets/tasks`，不要假定只有一个定义。日志中的 `all_results` 可能包含未通过阈值的诊断候选；出现候选不等于业务逻辑已经接受。

## 4. 常用功能修改位置

下列路径均以**源码根目录**为起点。打开文件后搜索“定位词”，比依赖行号更可靠。

### 4.1 商店体力、点数、回血和消费

| 功能 | 文件与定位词 | 当前值或判断 | 影响范围 |
| --- | --- | --- | --- |
| 商店顶部体力与 P 点数 | `agent/custom/shop.py` → `_read_shop_hud` | `float(rows[0].score) < .90` 时拒绝 | **两者共用**，修改一处会同时影响体力和余额 |
| 商店回血入口按钮 | 同文件 → `read_interval_heal_button` | `>= .90` | 是否确认“回复”按钮 |
| 回血弹窗各字段 | `agent/custom/interval_recovery.py` → `rows` | `>= .90` | 体力、回复量、消费前后余额、按钮等；不是只影响一个数字 |
| 咨询桌面重新进入 | `agent/custom/shop.py` → `read_consultation_desk_entry` | 标题和按钮 `>= .90` | 重新进入商店 |
| 饮料详情标题 | 同文件 → `owned_detail_title` | 标题、名称 `>= .90` | 饮料身份确认 |
| 丢弃饮料确认 | 同文件 → `read_discard_confirmation`、`owned_throw_box` | `0.90` | 名称、问题、确认及取消按钮 |
| 删牌选中标题 | `agent/custom/removal.py` → `DECK_TITLE_OCR_MIN_SCORE` | `0.80` | 还要求精确卡名与选中位置正确 |
| 删牌按钮/确认弹窗 | 同文件 → `read_delete_button`、`read_delete_confirmation` | 模板 `0.75`；OCR `0.90` | 模板与 OCR 是不同检查，不能只改一边 |
| 商店删牌取消按钮 | `agent/custom/produce/shop.py` → `buttons[0].score` | `>= .80` | 仅该取消分支 |
| 自定义弹窗 OCR | `agent/custom/customization.py` → `rows` | `>= .85` | 自定义界面中的文字与数字 |

商店 HUD 目前的固定框为：

```python
SHOP_HEALTH_ROI = [328, 48, 122, 42]
SHOP_POINTS_ROI = [328, 94, 122, 42]
```

两者都在图标右侧，使用 `only_rec=True`。`read_interval_health` 检查合法的当前值/最大值，`read_shop_points` 检查完整的数字或规范千位逗号；`0` 是有效余额，`None` 才代表未读到。

**示例：只调整这两个 HUD 字段共用的分数门槛。**

在 `_read_shop_hud` 中，将：

```python
if len(rows) != 1 or float(rows[0].score) < .90:
    return None
```

改为：

```python
if len(rows) != 1 or float(rows[0].score) < .88:
    return None
```

这是修改位置的演示，**不是建议所有人改成 0.88**。它会同时放宽体力与余额；不会放宽回血弹窗，也不会接受 `+19`、`P19`、非法体力分数或多个候选。若只想改其中一项，需要拆分函数参数，不能直接修改这个共用值。

商店商品价格由 `agent/custom/produce/shop.py` 的 `_recognize_price` 读取，并经过 `parse_shop_price` 解析；它没有和 HUD 共用 Python 的 `0.90`。刷新费用还使用 `shop.py` 的 `read_number`。不要把“余额”“商品价格”“刷新费用”当作同一个读数入口。

事件选择、工作类型等界面的体力/P 点数读取还在 `agent/custom/produce/events.py`、`options.py` 等文件中，可能直接调用 `ProduceRecognitionHealth`、`ProduceRecognitionPoint`。修改商店 HUD 门槛不会自动改变这些入口。

### 4.2 战斗出牌、卡牌名字和黑醋取牌

| 功能 | 文件与定位词 | 当前值或判断 |
| --- | --- | --- |
| 是否还在战斗场景 | `assets/resource/base/pipeline/ProduceUtils.json` → `ProduceRecognitionHealthFlag` | 模板 `threshold: 0.7`，不是体力数字 OCR |
| 卡牌检测框 | 同文件 → `ProduceRecognitionCards` | `NeuralNetworkDetect`，当前节点未显式写 `threshold` |
| 再动图标初筛 | `agent/custom/produce/battle.py` → `ProduceRecognitionExtraAction` | 调用时覆盖模板门槛为 `0.35` |
| 再动图标结论 | 同一识别函数内 `score >= 0.52`、`score <= 0.46` | `>= 0.52` 判再动；`<= 0.46` 判非再动；中间为未知 |
| 剩余回合数字 | `agent/custom/battle_drinks.py` → `parse_turn`、`_read_bonus` | `0.90`；数字与额外回合格式另行检查 |
| 已选中牌单区域标题 | 同文件 → `CardNameReader.RAISED_SINGLE_MIN_SCORE` | `0.95` |
| 已选中牌双区域一致核名 | 同文件 → `RAISED_AGREEMENT_MIN_SCORE` | `0.80`，**需要两个区域精确同名**，不能把它当作单区域门槛 |
| 普通牌名读取 | 同文件 → `CardNameReader.read` | 区域 OCR `0.93`，精确名称路径 `0.95` |
| 抬起卡牌/SELECT 标记 | 同文件 → `locate_raised` | 检测候选 `0.50`，SELECT OCR `0.95` |
| 黑醋移动页与按钮 | `agent/custom/battle_move.py` → `is_move_page`、`move_button` | OCR `0.90` |
| 黑醋选中牌标题 | 同文件 → `selected_title` | OCR `0.93` |

**示例：调整战斗体力图标的模板门槛。**

在 `ProduceUtils.json` 中，找到整个 `ProduceRecognitionHealthFlag` 节点，只修改它的 `recognition.param.threshold`：

```json
"threshold": 0.7
```

例如临时测试 `0.72` 是收紧要求，`0.68` 是放宽要求。保留 `roi`、模板路径和其他字段。这里的修改不会改变商店体力的 `0.90`，也不会取消战斗中连续帧复核。

**示例：显式设置卡牌检测框门槛。**

在 `ProduceRecognitionCards.recognition.param` 中增加：

```json
"threshold": [0.3]
```

这是显式写出当前 SDK 对该识别类型提供的默认值，并非优化建议。当前包的 Python SDK 定义见 `python/Lib/site-packages/maa/pipeline.py`：OCR 默认 `0.3`，模板匹配默认 `[0.7]`，检测模型默认 `[0.3]`。最终生效参数仍要以实际加载资源、运行时覆盖和日志为准。

`ProduceRecognitionCards` 被战斗、牌库及其他选卡路径共用，修改它可能影响多个场景。降低检测框门槛也不会自动通过卡名、稀有度、手牌区域和可用状态检查。不要为调整阈值替换 `cards.onnx`。

### 4.3 卡图、稀有度和饮料身份

| 功能 | 文件与定位词 | 当前值 | 说明 |
| --- | --- | --- | --- |
| 战斗完整卡图身份 | `agent/custom/hand_identity_calibration.json` → `gates.full` | `score: 0.4`、`margin: 0.09` | 两项都要通过 |
| 战斗遮挡卡图身份 | 同文件 → `gates.local` | `score: 0.4`、`margin: 0.17` | 使用可见局部；不能只降 score 忽略差距 |
| 方形卡牌检索 | `agent/custom/square_identity.py` | `MIN_SCORE=.56`、`MIN_MARGIN=.12` | 卡图身份，不等于 OCR 分数 |
| 饮料瓶图检索 | `agent/custom/drink_visual.py` | `MIN_SCORE=.78`、`MIN_MARGIN=.14` | 身份确认、使用及丢弃还会核对标题 |
| 卡框颜色稀有度 | `agent/custom/card_visual.py` | `MAX_KNOWN_DISTANCE=.18`、`MIN_DISTANCE_MARGIN=.07` | 距离越小越相近；放宽距离是调大 |
| 边缘稀有度模型 | 同文件 → `_classify_edge_rarity` | 最近距离上限 `0.10`，并要求邻近标签一致 | 不与上面的距离门槛混用 |
| 较早卡图检索路径 | 同文件 → `match_card_visual` | `best_score >= .15`、`margin >= .055` | 返回的 confidence 另有换算，不能直接当原始分数 |
| 卡名目录模糊匹配 | 同文件 → `match_card_catalog` | 长名字 `0.78`、短名字 `0.86`，领先差距 `0.06` | 另有长度至少 4、分数 `0.60`、差距 `0.18` 的分支 |
| 牌库身份接受 | `agent/custom/deck_scan.py` | `DECK_IDENTITY_MIN_CONFIDENCE=.80` | 与底层检索门槛是不同层 |
| 删除候选排序入口 | `agent/custom/produce/shop.py` | `name_confidence >= .55`；部分路径稀有度 `0.30` | 最终删除仍需选中后精确核名 |

修改 `hand_identity_calibration.json` 时，保留 `version`、`gallery_sha256` 和其他元数据。手动调整 gate 不会自动重新标定图集。`full` 与 `local` 的选择见 `agent/custom/hand_identity.py`，不能把它们简单理解为某个固定手牌张数。

代码中的 `matched.confidence == 1.0`、`>= .999` 有些用于判断精确目录命中。这些值不应当作普通 OCR 门槛随意降低，否则会改变“必须精确同名”的规则。

## 5. 用日志决定改哪一层

先查看运行包的 `debug/custom/日期.log` 和 `debug/maafw.log`，旧日志可能在 `maafw.bak.*.log`。文件名随版本和轮转而变，以实际目录为准。

| 看到的现象 | 先检查什么 |
| --- | --- |
| `all_results` 完全为空 | 是否截到了目标、ROI 是否正确、是否被弹窗遮挡、文字检测是否漏掉 |
| 文字正确但 `score` 低于门槛 | 确认是哪一层拒绝；再考虑只调整对应门槛 |
| 文字正确、分数高，但 `filtered_results` 为空 | `expected` 正则、类别筛选、框架阈值与覆盖参数 |
| 分数很高但数字/名字错误 | 原图质量、裁剪、模型或模板；降低门槛不会把错误结果改正确 |
| 第一候选分数高但仍为未知 | 第二候选是否太接近、`margin` 是否不足 |
| 只在出牌或购买动画中失败 | 页面阶段、遮罩、数字滚动和稳定性；不是优先降置信度 |
| 识别成功却不出牌/不购买 | 出牌回合规则、余额、状态、选中核名或扣款确认等业务条件 |

实际例子：旧商店体力框曾得到 `❤33/33`，三次分数约 `0.878～0.897`。最终采用固定数字框排除爱心，而没有降低 `0.90`。这种情况的处理对象是输入图像，不是接受门槛。

P 点数由 `379` 变成 `378`，也可能是扣款动画中间值。调整置信度不会让动画直接结束，仍要保留现有扣款核对。

## 6. 如何验证和恢复

1. 记录文件、函数/节点、原值、新值、原始截图和当时日志。
2. 一次调整一个功能的一层门槛；不要同时调整 ROI、模板、等待和多个分数。
3. 用同一批截图比较：目标清晰、目标模糊、相似卡牌、目标不存在、弹窗遮挡、动画过渡都要包含。
4. 确认漏识别减少的同时，没有把错误卡牌、错误数字或其他按钮当作目标。
5. 通过离线检查后做实际场景验证。涉及购买、删牌、喝药和回忆保存时，核对最终选择及消费结果。
6. 出现误识别就恢复备份并重新启动；不要继续降低其他门槛来掩盖它。

在有测试依赖的源码环境中，可执行：

```powershell
python -m compileall -q agent
python -m pytest tests/test_health_recognition.py tests/test_healing_steps.py -q
```

其他相关测试可搜索：

- 战斗和牌名：`test_battle_selected_identity.py`、`test_card_rule_raised_identity.py`、`test_hand_identity.py`。
- 饮料和黑醋：`test_battle_drinks.py`、`test_national_vinegar.py`。
- 卡图：`test_square_identity.py`。
- 回忆和结算：`test_memory_deck_flow.py`、`test_memory_settlement_handoff.py`。

便携包自带 Python，但不保证包含 pytest 和源码测试。运行包可先用 `.\python\python.exe -m compileall -q agent` 检查语法；语法通过不等于游戏识别通过。不要为运行测试把个人配置复制到公开仓库。
